# Hermes Studio 定制开发工作流

> 基于上游 main @ `781df5fa`　|　定制分支：`custom`　|　建立日期：2026-07-27
> 本文档记录基于开源项目 hermes-studio 做二次定制开发的分支策略、上游同步流程与冲突处理规范。
> 环境准备与启动见 [项目启动指南](./项目启动指南.md)；功能模块全览见 [功能模块文档](./功能模块文档.md)。

## 1. 背景与目标

hermes-studio（https://github.com/EKKOLearnAI/hermes-studio）是开源项目，本项目基于它做二次定制开发，需要：

- **持续跟进上游新功能** —— 上游频繁迭代，需定期同步
- **保留本地定制** —— 对部分源码有自定义修改，不能被上游覆盖丢失
- **可备份可恢复** —— 定制成果要有远程备份，防本地丢失

为此采用「**main 镜像上游 + custom 承载定制 + rebase 同步**」工作流。

## 2. 分支与远程结构

### 2.1 分支

| 分支 | 作用 | 规则 |
|---|---|---|
| `main` | 上游纯镜像 | 只 `git pull --ff-only origin main`，**绝不在此写代码** |
| `custom` | 承载本地定制 | 所有定制以提交形式保留，通过 `rebase` 始终踩在上游最新之上 |

### 2.2 远程

| remote | 仓库 | 用途 |
|---|---|---|
| `origin` | EKKOLearnAI/hermes-studio | 上游，**只拉**新功能 |
| `myfork` | yhwork/hermes-studio | 你的 fork，**推** custom 备份 |

```
origin (上游)  ──●──●──●──●──●──>  main   (纯镜像, ff-only)
                          │
                          │ rebase
                          ▼
myfork (fork)  ──●──●──●──●──>  custom (定制, 推送备份)
                 你的定制提交
```

## 3. 初始设置记录（2026-07-27 已完成）

以下为建立工作流时执行的操作记录，仅供参考，**无需重复执行**：

```bash
# 1. 开启冲突记忆（rerere 记住冲突解法，下次自动套用）
git config rerere.enabled true

# 2. 把当时散落的本地改动固化为定制提交
git checkout -b custom
git add -A
git commit -m "custom: 本地定制功能"

# 3. main 干净快进到上游最新
git checkout main
git pull --ff-only origin main

# 4. 定制变基到上游之上（冲突在此解决）
git checkout custom
git rebase main

# 5. 配置 fork 远程并推送备份
git remote add myfork https://github.com/yhwork/hermes-studio.git
git push -u myfork custom
```

## 4. 日常同步流程

### 4.1 一键同步（推荐）

用脚本自动完成「检查 + 同步 + 备份」：

```bash
bash scripts/sync-upstream.sh            # 完整同步并推送备份
bash scripts/sync-upstream.sh --check    # 仅查看状态，不执行
bash scripts/sync-upstream.sh --no-push  # 同步但不推 fork
```

脚本自动：检查工作区干净 → main 快进拉取 → custom 变基（rerere 已解决的冲突自动续跑）→ 强推 myfork 备份。遇源码冲突会停下给出手动解决指引。

> PowerShell/cmd 终端用 `scripts\sync-upstream.cmd`（自动定位 bash.exe，等价）。

### 4.2 手动同步（等价的 4 步）

脚本背后等价于以下 4 步：

```bash
# 1. main 拉取上游新功能（纯快进）
git checkout main
git pull --ff-only origin main

# 2. 切到定制分支
git checkout custom

# 3. 定制重放到新基础之上（rerere 自动解 openapi 冲突）
git rebase main

# 4. 备份到 fork（rebase 改写历史，需强推）
git push -f myfork custom
```

> 同步前可预览上游新增提交：`git fetch origin && git log main..origin/main --oneline`

## 5. 冲突处理

> rebase / cherry-pick 中 `--ours` = HEAD = 上游(main)，`--theirs` = 被应用的提交 = custom。

### 5.1 docs/openapi.json —— 取上游

本地曾有一份残缺的 openapi.json（2829 行 vs 上游 13283 行），约定**冲突时一律取上游版本**：

```bash
git checkout --ours docs/openapi.json   # 取上游版
git add -f docs/openapi.json            # 因 .gitignore 含 docs/，需 -f 强制
```

> rerere 已记录此解法，后续同步会自动套用，通常无需手动处理。
> 若定制确实改了 API，应在同步完成后重新生成 spec，而非保留过期版本。

### 5.2 package-lock.json —— 取一端后重装

锁文件是自动生成的，不要手动合并：

```bash
git checkout --ours package-lock.json   # 取上游版（定制未改依赖时）
# 或 git checkout --theirs package-lock.json  # 取定制版（定制改了依赖时）
npm install                              # 根据 package.json 重新生成正确锁文件
git add package-lock.json
```

### 5.3 源码文件 —— 手动合并

`ChatInput.vue` 等源码定制冲突，需手动检查保留你的逻辑。建议借助 IDE 三向合并工具，解决后：

```bash
git add <冲突文件>
git rebase --continue
```

## 6. 开发纪律

1. **`main` 绝不写代码** —— 它只是上游镜像，保持干净快进
2. **所有定制只进 `custom`** —— 改代码前确认分支：`git branch --show-current`
3. **`origin` 只拉不推，`myfork` 才推** —— 不污染上游
4. **rebase 后强推 fork** —— `git push -f myfork custom`，rebase 改写了 custom 历史
5. **同步前先确认工作区干净** —— `git status` 无未提交改动再开始

## 7. 故障排除

### rebase 中途搞砸了

```bash
git rebase --abort    # 放弃 rebase，回到操作前状态
```

### 定制提交丢失（如误用 --skip）

原提交仍在 reflog，可恢复：

```bash
git reflog                            # 找到原定制提交哈希（如 eb2dfbe1）
git cherry-pick <哈希>                 # 重新应用，再按第 5 节解决冲突
```

### 想看当前定制了哪些东西

```bash
git diff main..custom --stat          # 定制文件清单
git diff main..custom -- <文件>       # 某文件的具体定制内容
```

### fork 上的 custom 落后了

```bash
git push -f myfork custom             # 强推覆盖 fork 上的旧版本
```

### 换电脑/重装后恢复定制

```bash
git clone https://github.com/yhwork/hermes-studio.git
cd hermes-studio
git checkout custom                   # 定制分支就在了
git remote add origin https://github.com/EKKOLearnAI/hermes-studio.git
git config rerere.enabled true        # 重新开启 rerere
```
